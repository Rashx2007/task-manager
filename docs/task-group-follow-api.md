# اتصال کنترل‌شدهٔ API پیگیری گروهی

## دامنهٔ این مرحله

مسیر جدید `/api/task-groups/follow` اضافه می‌شود. رابط فعلی، API مستقل `/api/follow` و API فقط‌خواندنی `/api/task-groups` تغییر نمی‌کنند. این مرحله گروه یا عضو ایجاد نمی‌کند و SQL جدید لازم ندارد.

GET فقط خواندنی است. POST و PUT به سرویس تراکنشی مرحلهٔ قبل متصل‌اند و فقط برای یک گروه موجود با نسخه و دریافت‌کنندگان صریح قابل استفاده‌اند. هیچ تیک، گروه‌ساز، گزینهٔ منو یا فراخوان خودکار از مودال فعلی اضافه نمی‌شود. DELETE و PATCH فعال نیستند.

## GET — خواندن زمینهٔ پنجره

`GET /api/task-groups/follow?taskId=TASK_ID`

فقط یک taskId مجاز است؛ شناسهٔ ناموجود/نامعتبر یا تکرار پارامتر خطا می‌دهد. زیرساخت گروه‌ها باید نصب و تأیید شده باشد. خروجی:

- `taskId`: همان کار درخواست‌شده.
- `group`, `members`, `warnings`: snapshot موجودِ گروه و دستگاه‌های اعضا.
- `follows`: فقط پیگیری‌های همان TaskID، با ترتیب شروع نزولی و سپس FollowID نزولی.

هر ردیف پیگیری شامل داده‌های قبلی متن/زمان و این اطلاعات است:

| فیلد | معنا |
| --- | --- |
| `BatchID` | شناسهٔ مشترک سابقهٔ گروهی؛ برای ردیف مستقل null |
| `BatchGroupID` | گروهِ همان سابقه، نه لزوماً گروه فعلی کار |
| `BatchOriginTaskID` | کارِ ایجادکنندهٔ اولیهٔ batch؛ ممکن است دیگر عضو جاری نباشد |
| `IsGroupLinked` | ردیف پیوند گروهی دارد |
| `CanEditGroup` | اشارهٔ نمایشی: این ردیف از batch گروه فعلی است |
| `CanEditIndependent` | اشارهٔ نمایشی: کار گروه جاری ندارد و ردیف هم مستقل است |
| `RequiresExplicitGrouping` | کار اکنون گروه دارد ولی ردیف قدیمی مستقل است؛ تبدیل صریح لازم است |

این پرچم‌ها مجوز امنیتی یا اجازهٔ ذخیره با snapshot کهنه نیستند. سرویس نوشتنی، نسخه و عضویت و دریافت‌کنندگان و مالکیت را زیر قفل دوباره بررسی می‌کند. وضعیت SyncEnabled در اعضای snapshot است؛ تغییر پایدار آن از این endpoint انجام نمی‌شود.

ردیفِ مربوط به یک گروه تاریخی، پس از خروج کار یا انتقال به گروه دیگر همچنان با BatchID اصلی دیده می‌شود؛ خودکار مستقل یا عضو batch جدید فرض نمی‌شود. متن مشابه، جای BatchID را نمی‌گیرد.

### جلوگیری از مخلوط‌شدن زمینه

خواندن از helper گروه موجود آغاز می‌شود. ردیف‌ها از نظر TaskID، یکتایی FollowID، مالک پیوند و کامل‌بودن شناسهٔ batch بررسی می‌شوند. پس از خواندن، عضویت جاری، فعال‌بودن گروه و نسخهٔ آن دوباره بررسی می‌شوند.

برای تشخیص چرخهٔ «ورود سپس خروج» نیز اثر عضویت‌های تاریخی با MemberID رشته‌ای و rowversion قبل/بعد مقایسه می‌شود؛ شناسهٔ bigint به Number جاوااسکریپت تبدیل نمی‌شود. این روش به قرارداد حفظ تاریخچه و افزایش نسخه در نویسندگان گروه تکیه دارد؛ تغییر مستقیم دیتابیس خارج از قرارداد برنامه مجاز فرض نمی‌شود.

در تغییر قابل‌تشخیص، خطای 409 با کد `GROUP_FOLLOW_CONTEXT_CHANGED` می‌آید؛ caller باید context را دوباره دریافت کند، نه اینکه دادهٔ ناقص را قابل ذخیره بداند. این خواندن خوش‌بینانه است و تضمین snapshot تراکنشی/serializable برای همهٔ ویرایش‌های مستقل هم‌زمان نمی‌دهد. در هر حال، پیگیریِ متعلق به TaskID دیگر نمایش داده نمی‌شود و حفظ ایمنی ذخیره به کنترل دوبارهٔ سرویس نوشتنی وابسته است.

## POST — ثبت تازه

بدنهٔ JSON همان قرارداد `createGroupFollow` در `docs/task-group-follow-write.md` است: گروه، کار پنجره، نسخه، RequestID پایدار، دریافت‌کنندگان صریح، متن و زمان و گزینهٔ کپی شرح.

خروجی موفق: `{ success: true, data: result }` با BatchID جدید و نگاشت taskId/followId و نسخهٔ گروه. تکرار درخواست یکسان رسید قبلی را با replayed=true می‌دهد؛ نسخهٔ آن رسید الزاماً نسخهٔ فعلی گروه نیست و برای عملیات بعدی باید snapshot تازه خواند.

## PUT — ویرایش متناظر

همان قرارداد POST به‌علاوهٔ BatchID و FollowID نسخهٔ متعلق به کار پنجره. فقط batch موجود همان گروه و همان پیوند منبع قابل ویرایش است. اعضای انتخاب‌نشده دست‌نخورده می‌مانند. دریافت‌کنندهٔ جاریِ صریح که در این batch ردیف ندارد، طبق سرویس یک نسخهٔ تازه از همین سابقه می‌گیرد؛ همهٔ تاریخچهٔ قدیمی کپی نمی‌شود.

ردیف مستقل قدیمی بدون BatchID معتبر خودکار به گروه تبدیل نمی‌شود. تبدیل صریح با پیش‌نمایش/تأیید، حذف گروهی، جداسازی سابقه، ایجاد گروه و مدیریت اعضا هنوز مرحله‌های بعدی‌اند. مسیر مستقل برای اعضای جاری گروه همچنان guard دارد.

## خطاها و استقرار

همهٔ پاسخ‌ها `Cache-Control: no-store` دارند. JSON خراب خطای 400 می‌دهد؛ خطاهای موردانتظار سرویس با کد و وضعیت کنترل‌شده برمی‌گردند و جزئیات خصوصی SQL منتشر نمی‌شوند. RequestID و نسخه و BatchID باید به همان عملیات/پنجره تعلق داشته باشند؛ در خطا، caller نباید با ساختن RequestID تازه همان عملیاتِ احتمالاً انجام‌شده را کورکورانه تکرار کند.

این مرحله سامانهٔ احراز هویت/مجوز انسانی جدید اضافه نمی‌کند. عضویت دستگاه/کار در گروه با هویت و سطح دسترسی کاربر متفاوت است. API مانند سایر APIهای داخلی باید در لایهٔ استقرار در برابر دسترسی نامجاز شبکه محافظت شود.

## آزمون این مرحله روی سیستم کاربر

فقط GET برای یک کار موجود اجرا شود. اگر گروهی ساخته نشده باشد، group=null و members=[] طبیعی است. follows می‌تواند خالی یا شامل سوابق مستقل باشد. خواندن نباید هیچ رکوردی ایجاد/ویرایش/حذف کند.

برای آزمون POST/PUT روی دیتابیس واقعی، گروه یا عضو با SQL دستی نسازید. آزمون نوشتنی واقعی به مرحلهٔ مدیریت گروه و فعال‌سازی کنترل‌شده موکول است. در این مرحله آزمون‌های HTTP/SQL با دوبل اجرا می‌شوند؛ اجرای Next.js و SQL Server واقعی روی سیستم کاربر جداگانه باید تأیید شود.
