# زیرساخت گروه کارها — مرحلهٔ اول

## وضعیت فعال‌سازی

این مرحله فقط فایل‌های زیرساخت را اضافه می‌کند. هیچ مسیر API، رابط کاربری، زمان‌بندی یا سابقهٔ موجودی به آن متصل نشده است. اعمال پچ با اجرای migration متفاوت است؛ برنامه migration را خودکار اجرا نمی‌کند.

تا پیش از تکمیل زمان‌بندی گروهی و مسیرهای پیگیری، ساخت گروه فعال از طریق SQL دستی یا API موقت مجاز نیست؛ زیرا مسیرهای فعلی هنوز گروه‌آگاه نیستند.

## ساختار

| جدول | مسئولیت |
| --- | --- |
| `TaskGroup` | عنوان، وضعیت و نسخهٔ گروه |
| `TaskGroupMember` | تاریخچهٔ عضویت و وضعیت شرکت در همگام‌سازی؛ هر کار حداکثر یک عضویت جاری |
| `TaskGroupFollowBatch` | هویت یک ثبت پیگیری مشترک |
| `TaskGroupFollowLink` | اتصال نسخهٔ هر کار به پیگیری مشترک؛ مالکیت واقعی ردیف با کلید خارجی مرکب کنترل می‌شود |
| `TaskGroupOperation` | زیرساخت ثبت شناسهٔ درخواست و نتیجه، برای جلوگیری از تکثیر عملیات پس از تلاش مجدد؛ استفاده از آن در مسیرهای آینده الزامی است |
| `TaskGroupMigration` | ثبت نسخهٔ نصب زیرساخت |

Migration ردیف‌های موجود کارها، زمان‌ها و سوابق را تغییر نمی‌دهد. تنها تغییر در جدول موجود، افزودن یک ایندکس یکتای مرکب روی `Follow_tbl(FollowID, TaskID)` برای کنترل مالکیت است. کلید اصلی موجود `FollowID` حفظ می‌شود. هیچ حذف آبشاری تعریف نشده است.

زمان‌های `datetime2` این جدول‌ها، زمان ثبت رویدادهای سیستمی و UTC هستند. قرارداد زمان دیواری کارها و پیگیری‌های موجود تغییر نکرده است.

## آزمون مستقل، بدون اتصال به دیتابیس

از ریشهٔ پروژه اجرا شود:

```powershell
node --experimental-vm-modules --test tests/task-groups.test.mjs
```

این آزمون‌ها کنترل ورودی، آمادگی زیرساخت، مالکیت، نسخه و مسیر rollback را با اتصال شبیه‌سازی‌شده بررسی می‌کنند. پیام `ExperimentalWarning` مربوط به ابزار داخلی آزمون Node است. نتیجهٔ این آزمون، اثبات اجرای SQL روی SQL Server نیست.

## اجرای migration — عملیات جداگانه و دستی

فایل: `database/migrations/20261025_001_task_groups.sql`

- ابتدا پشتیبان قابل‌بازگردانی تهیه و نام دیتابیس متصل به برنامه را از تنظیمات واقعی تعیین کنید؛ نام دیتابیس حدس زده نشود.
- در بازهٔ نگهداری، نوشتن برنامه متوقف شود؛ ساخت ایندکس می‌تواند جدول سوابق را قفل کند.
- در SSMS دیتابیس صحیح را صریحاً انتخاب کنید و کل فایل را یکجا اجرا کنید. اسکریپت عمداً `USE` ندارد و دیتابیس‌های سیستمی را رد می‌کند.
- عملیات در تراکنش با قفل نصب اجرا می‌شود. موفقیت فقط پس از پیام `Applied successfully` و کنترل جدول‌ها و قیدها پذیرفته شود.
- اجرای مجدد نسخهٔ ثبت‌شده، در صورت وجود جدول‌های موردنیاز، بدون ایجاد مجدد پایان می‌یابد. این نتیجه جای بررسی سلامت قیدها را نمی‌گیرد؛ کنترل زمان اجرای کتابخانه قیدهای ضروری را نیز بررسی می‌کند.
- هر خطا نیازمند بررسی است؛ جدول‌های متعارض یا ایندکس‌ها را برای دورزدن خطا حذف نکنید.
- اسکریپت حذف خودکار ارائه نشده است: پس از ایجاد سوابق گروهی، حذف جدول‌ها تاریخچه را از بین می‌برد.

## قرارداد استفاده از کتابخانه در مرحلهٔ بعد

`lib/task-groups.js` فقط سمت سرور استفاده شود. هیچ ورودی کاربر مستقیماً به SQL الحاق نمی‌شود.

- عملیات تغییر گروه باید از `runTaskGroupTransaction` و همان تابع `tx` استفاده کند؛ فراخوانی `query` عمومی در callback تراکنش ممنوع است.
- `expectedVersion` از نسخهٔ مشاهده‌شدهٔ گروه می‌آید، نه از یک دریافت تازه و پنهانی هنگام ذخیره. تغییر هم‌زمان باید خطای تعارض بدهد.
- فهرست دریافت‌کنندگان صریح و با `resolveSyncTargets` تأیید شود. عضو گروه دیگر، عضو خارج‌شده و عضو مستثنا پذیرفته نمی‌شود. هیچ دریافت‌کننده‌ای خودکار جایگزین فهرست ارسالی نشود.
- برداشتن تیک یک عملیات با `SyncEnabled` دائمی یکی نیست: انتخاب همان عملیات فهرست دریافت‌کنندگان را محدود می‌کند؛ فقط پاسخ صریح کاربر به پیام پایان می‌تواند وضعیت شرکت در عملیات بعدی را تغییر دهد.
- `assertFollowOwner` پیش از ویرایش ردیف اجرا شود. برای ویرایش مشترک، علاوه بر مالکیت، شناسهٔ `BatchID` و پیوند متناظر هر عضو باید کنترل شود؛ صرف شباهت متن کافی نیست.
- حذف پیگیری مشترک، تکلیف پیوندهای آن را صریح تعیین کند؛ حذف آبشاری یا حذف بی‌خبر ردیف‌های دیگر ممنوع است.
- ایجاد گروه جدید، افزودن/حذف عضو، انحلال، ثبت درخواست تکرارناپذیر و انتقال بین گروه‌ها هنوز پیاده‌سازی نشده‌اند. این wrapper برای تغییر یک گروه موجود است؛ برای انتقال چندگروهی، قفل‌ها باید در یک تراکنش و به ترتیب `GroupID` گرفته شوند؛ wrapper نباید تو در تو فراخوانی شود.
- هر تغییر عضویت، وضعیت همگام‌سازی و پیگیری مشترک باید نسخهٔ گروه را به‌روز کند. کنترل نسخهٔ متن و زمان ویرایش‌شده نیز هنگام اتصال مسیرهای واقعی تکمیل شود.
- زمان‌بندی خودکار و تشخیص تداخل باید پیش از فعال‌سازی عمومی، گروه را واحد برنامه‌ریزی بدانند. هیچ گروه فعالی با زمان‌بند فعلی ایجاد نشود.
- اضافه‌شدن عضو یا بازگشت از استثنا به‌معنی کپی عقب‌گردی سوابق نیست. سوابق و اعضای گذشته پس از جداسازی حفظ شوند.

## محدودهٔ اعتبارسنجی

آزمون‌های Node و بررسی اعمال پچ قابل اجرا هستند. اجرای migration، ساخت واقعی قیدها، rollback دیتابیس و آزمون هم‌زمانی چند اتصال باید روی SQL Server آزمایشی دارای ساختار فعلی انجام شوند؛ هنوز جایگزینی برای این آزمون‌ها وجود ندارد.
