# سرویس ثبت و ویرایش پیگیری گروهی — مرحلهٔ داخلی

## وضعیت فعال‌سازی

هستهٔ سرویس به‌تنهایی دکمه، گروه یا عضوی را فعال/ایجاد نمی‌کند. اتصال کنترل‌شدهٔ HTTP در `/api/task-groups/follow` و قرارداد خواندن زمینه در `docs/task-group-follow-api.md` مستند شده‌اند. API مستقل `/api/follow` و مودال فعلی به سرویس گروهی وصل نشده‌اند و guard آن‌ها برای عضو گروه پابرجاست. SQL جدید لازم نیست؛ سرویس از جدول‌های migration گروه‌ها با نسخهٔ `20261025_001_task_groups` استفاده می‌کند.

فایل سرویس: `lib/task-group-follow-service.js`

- `createGroupFollow(body)` — ایجاد یک مجموعهٔ تازهٔ پیگیری متناظر.
- `updateGroupFollow(body)` — ویرایش نسخه‌های منتخبِ یک مجموعهٔ شناخته‌شده.
- `groupFollowFailure(error)` — نگاشت خطای کنترل‌شده برای اتصال بعدی API.

در این مرحله هیچ روش آماده‌ای برای ایجاد گروه در دیتابیس کاربر ارائه نمی‌شود. گروه یا عضو را با SQL دستی برای آزمون ایجاد نکنید.

## قرارداد ورودی برای اتصال بعدی

هر عملیات به این فیلدها نیاز دارد:

| فیلد | قرارداد |
| --- | --- |
| `groupId` | شناسهٔ مثبت گروه |
| `taskId` | کارِ پنجرهٔ فعلی؛ باید عضو جاری گروه باشد |
| `expectedGroupVersion` | نسخهٔ ۱۶رقمی hex از snapshot گروه |
| `requestId` | UUID غیرتهی و پایدار برای همین عملیات منطقی |
| `recipientTaskIds` | آرایهٔ صریح و غیرخالیِ شناسهٔ دریافت‌کنندگان، حداکثر ۲۵۰ ورودی |
| `description` | متن غیرخالی |
| `dueDateTime`, `endDateTime` | زمان دیواری معتبر با همان قرارداد پیگیری مستقل |
| `updateDescription` | boolean؛ در صورت true، شرح کارِ دریافت‌کنندگان نیز کپی می‌شود |

ویرایش علاوه بر این‌ها `batchId` و `followId` می‌خواهد: FollowID باید نسخهٔ متناظر همان TaskID پنجره در همان batch باشد. ثبت تازه نباید batchId یا followId قبلی داشته باشد.

اعتبارسنجی متن، بازه و زمان از `parseFollowFields` مشترک با پیگیری مستقل استفاده می‌کند. دقت ثانیهٔ موجود حفظ می‌شود. برچسب Z قدیمی، ساعت دیواری است و تبدیل منطقهٔ زمانی اعمال نمی‌شود.

## معنای انتخاب و استثنا

- دریافت‌کننده از TaskID یا اعضای گروه حدس زده نمی‌شود؛ آرایهٔ صریح لازم است.
- هر دریافت‌کننده باید اکنون عضو همین گروه و `SyncEnabled=1` باشد. انتخاب عضو خارج‌شده، عضو گروه دیگر یا عضو مستثنا کل عملیات را رد می‌کند.
- خود کارِ پنجره می‌تواند تیک نداشته باشد. در این حالت برای آن پیگیری یا شرح جدیدی نوشته نمی‌شود، حتی اگر متن از ویرایشگر همین کار آمده باشد.
- استثنای یک عملیات، عضویت یا SyncEnabled را تغییر نمی‌دهد؛ بازگشت خودکار یا کپی عقب‌گردی رخ نمی‌دهد.
- سؤال بازگشت مستثناها هنگام بستن، و تغییر پایدار SyncEnabled، در این مرحله پیاده نشده‌اند؛ در رابط و مسیر مدیریت گروه باید جدا طراحی/متصل شوند.

## ایجاد و ویرایش نسخه‌های متناظر

ثبت تازه یک BatchID سمت سرور تولید می‌کند؛ برای هر دریافت‌کننده یک ردیف Follow و یک پیوند `(BatchID, TaskID, FollowID)` می‌سازد. سوابق مستقل قبلی حتی اگر متن یکسان داشته باشند، پیدا یا بازنویسی نمی‌شوند.

در ویرایش:

1. گروه، نسخهٔ گروه، منبع و تمام پیوندهای batch دوباره زیر قفل بررسی می‌شوند.
2. برای دریافت‌کننده‌ای که پیوند دارد، فقط همان FollowID با شرط هم‌زمان FollowID و TaskID تغییر می‌کند.
3. برای یک عضو جاریِ صریحاً انتخاب‌شده که هنوز نسخه‌ای از این batch ندارد، یک نسخه و پیوند تازه ایجاد می‌شود؛ این، کپی صریح همان سابقه است نه انتقال همهٔ تاریخچهٔ قدیمی.
4. نسخه‌های دریافت‌کنندگانِ انتخاب‌نشده و اعضای سابق بدون تغییر باقی می‌مانند؛ حتی اگر پس از استثنا متن/زمان آن‌ها با بقیه متفاوت شود.
5. اگر پیوندی به پیگیری حذف‌شده یا مالک نامرتبط اشاره کند، کل عملیات رد می‌شود؛ بازسازی حدسی انجام نمی‌شود.

متن، شروع و پایان و مدت فقط برای دریافت‌کنندگان منتخب همگام می‌شوند. کد کار، دستگاه، وضعیت، اولویت، زمان‌بندی کار و تاریخ اتمام خودکار یکسان نمی‌شوند. کپی شرح نیز فقط در صورت درخواست و فقط برای منتخب‌ها انجام می‌شود.

تبدیل یک پیگیری مستقل قدیمی به batch، حذف گروهی پیگیری و جداسازی یک پیگیری از batch هنوز به این سرویس اضافه نشده‌اند. خواندن context بدون تغییر داده، در مسیر API جداگانه مستند شده است. در نبود BatchID معتبر، ویرایش گروهی یک ردیف قدیمی خودکار فرض نمی‌شود؛ مسیر تبدیل باید در مرحلهٔ بعد صریح و قابل‌تأیید باشد.

## تراکنش، نسخه و تکرار درخواست

ترتیب اجرا روی همان اتصال `runTransaction`:

1. قفل زمان‌بندی `task-manager:schedule`.
2. تأیید نصب و قیدهای زیرساخت گروه‌ها.
3. قفل انحصاری همان گروه با helper موجود `lockGroup`.
4. بررسی RequestID در TaskGroupOperation زیر قفل.
5. در عملیات تازه، کنترل نسخهٔ گروه و عضویت/گیرندگان و قفل کارها با ترتیب شناسهٔ صعودی.
6. ثبت/ویرایش پیگیری‌ها، پیوندها و کپی اختیاری شرح.
7. لمس batch در ویرایش و افزایش نسخهٔ گروه.
8. ذخیرهٔ نتیجه و hash درخواست در TaskGroupOperation؛ سپس commit.

شکست هر نوشتن، از جمله ثبت نتیجهٔ عملیات، همهٔ تغییرات را rollback می‌کند. خطای یکی از گیرندگان، موفقیت جزئی ایجاد نمی‌کند.

RequestID باید برای تکرار همان درخواست حفظ شود. hash از نوع عملیات، گروه، کارِ پنجره، نسخهٔ مورد انتظار، منبع و زمان‌های نرمال، متن، گزینهٔ کپی و شناسه‌های مرتب/بدون تکرار ساخته می‌شود.

- همان RequestID + همان محتوا: نتیجهٔ ذخیره‌شده با `replayed=true` برمی‌گردد؛ پیگیری، پیوند یا نسخهٔ تازه ایجاد نمی‌شود.
- همان RequestID + محتوای متفاوت: `REQUEST_ID_REUSED`؛ هیچ تغییر تازه‌ای انجام نمی‌شود.
- RequestID تازه + نسخهٔ کهنه: `GROUP_CHANGED`؛ دریافت snapshot جدید لازم است.
- درخواست قبلاً commit‌شده حتی اگر اکنون گروه بسته یا عضویت عوض شده باشد، فقط رسید عملیات قبلی را برمی‌گرداند، نه نوشتن تازه.

نسخهٔ موجود در یک رسید replay، نسخهٔ پس از همان عملیات قدیمی است؛ الزاماً نسخهٔ فعلی گروه نیست. UI باید پیش از عملیات بعدی snapshot تازه بخواند. صرف دریافت replay مجوز ذخیره با نسخهٔ قدیمی نیست.

سرویس جدید به wrapper قبلی `runTaskGroupTransaction` تو در تو متصل نشده است؛ برای بررسی رسید پیش از کنترل نسخه، همان helperهای قفل را با ترتیب قبلی در یک تراکنش مستقل استفاده می‌کند. رفتار wrapper قبلی تغییر نکرده؛ فقط helper قفل آن export شده است.

## خروجی موفق

خروجی شامل RequestID، نوع عملیات، GroupID، TaskID پنجره، BatchID، نسخهٔ جدید گروه، فهرست دریافت‌کنندگان، فهرست اعضای فعلیِ انتخاب‌نشده، نگاشت taskId/followId منتخب‌ها و replayed است. برای نمایش UI یا اجازهٔ عملیات بعدی، snapshot فعلی باید دوباره بررسی شود.

## مرز زمان و لاگ

این سرویس هیچ ستونی از TimeDate_tbl، تاریخ اتمام، وضعیت کار، زمان‌بندی کار یا TaskStatusHistory را نمی‌نویسد. زمانِ خود پیگیری در Follow_tbl ثبت می‌شود. سوابق و مقادیر قدیمی نیز خودکار اصلاح نمی‌شوند.

TaskGroupOperation در این مرحله برای جلوگیری از اجرای تکراری و نگهداری رسید است، نه تاریخچهٔ کامل متن قبل/بعد همهٔ ویرایش‌ها. نگهداری دائمی یا پاک‌سازی رسیدها باید جداگانه با سیاست جلوگیری از تکرار تصمیم‌گیری شود؛ حذف دستی رسید می‌تواند امکان اجرای دوبارهٔ RequestID قدیمی را ایجاد کند.

## آزمون و محدودیت

آزمون‌های این مرحله ماژول‌های واقعی helper و سرویس را با دوبل SQL اجرا می‌کنند؛ شامل rollback شبیه‌سازی‌شده در نقاط نوشتن، مالکیت، استثنا، نسخهٔ کهنه و تکرار درخواست‌اند. این‌ها اجرای SQL یا رقابت چند اتصال روی SQL Server واقعی نیستند. ویندوز در این محیط در دسترس نیست؛ مسیر فایل آزمون با fileURLToPath نوشته شده است.

تا تکمیل رابط و مدیریت گروه، آزمون نوشتنی واقعی روی دیتابیس کاربر انجام نشود. آزمون GET مسیر API، فقط خواندنی است. برنامهٔ عادی فقط از مسیر پیگیری مستقلِ تأییدشده استفاده می‌کند.
