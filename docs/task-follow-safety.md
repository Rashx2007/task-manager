# ایمنی پیگیری مستقل پیش از فعال‌سازی پیگیری گروهی

## دامنهٔ این مرحله

این مرحله زیرساخت ثبت/ویرایش/حذف پیگیری مستقل را ایمن می‌کند؛ گروه یا پیگیری گروهی ایجاد نمی‌کند و SQL جدید لازم ندارد. فایل‌های فعلی DatePicker و انتخابگر ساعت و منطق همگام‌سازی دستی شروع/پایان دست‌نخورده‌اند.

## جداسازی زمان پیگیری از زمان اتمام

- POST و PUT و DELETE پیگیری، دیگر هیچ ستونی از `TimeDate_tbl` را تغییر نمی‌دهند؛ به‌خصوص `Finish_DateTime` با MAX پایان پیگیری‌ها بازنویسی نمی‌شود.
- زمان شروع و پایان خود پیگیری در `Follow_tbl` باقی می‌ماند. برنامه برای نمایش آخرین فعالیت، می‌تواند مانند مسیر زمان‌بند موجود از `MAX(Follow_tbl.EndDateTime)` استفاده کند؛ فعالیت معادل اتمام نیست.
- وضعیت کار، زمان‌های برنامه‌ای و تاریخچهٔ تغییر وضعیت نیز در این عملیات تغییر نمی‌کنند. این مرحله لاگِ ویرایش متن پیگیری تولید نمی‌کند؛ TaskStatusHistory همچنان برای تغییر وضعیت است.
- هیچ مقدار قدیمیِ `Finish_DateTime` پاک یا بازسازی نمی‌شود. اگر لازم باشد یک مقدار قدیمی اصلاح شود باید با مدرک و عملیات موردی جدا بررسی شود.

## تراکنش و مالکیت

- ایجاد پیگیری و کپی اختیاری متن به شرح همان کار روی یک اتصال و تراکنش انجام می‌شوند. شکست یکی، دیگری را نیز rollback می‌کند.
- همهٔ نوشتن‌ها ابتدا قفل مشترک زمان‌بندی `task-manager:schedule` و سپس قفل ردیف کار را می‌گیرند تا با مسیر اتمام و زمان‌بندی هماهنگ باشند.
- PUT و DELETE، هم `FollowID` و هم `TaskID` صریح می‌خواهند. شناسهٔ کار از یک پیگیری دیگر استنباط نمی‌شود. شرط هر دو شناسه روی خود UPDATE/DELETE نیز وجود دارد.
- DELETE اکنون قرارداد `?id=FOLLOW_ID&taskId=TASK_ID` دارد. مودال همراه پچ به‌روز شده؛ فراخوان قدیمی بدون TaskID رد می‌شود.
- خطای SQL با جزئیات داخلی به کاربر برنمی‌گردد. خطای تعلق، کار ناموجود، ساختار ناقص و وابستگی ارجاعی پیام کنترل‌شده دارند.
- حذف پیگیری، متن قبلاً کپی‌شده در شرح کار را خودکار بازگردانی نمی‌کند؛ نسخهٔ قبلی شرح در این API موجود نیست و حدس زده نمی‌شود.

## زمان و اعتبارسنجی

- شناسه‌ها اعداد صحیح مثبت int32 هستند؛ ارقام فارسی و عربی با helper موجود نرمال می‌شوند.
- متن باید غیرخالی باشد و updateDescription فقط boolean است.
- زمان استاندارد دیواری `YYYY-MM-DD HH:mm:ss` و شکل قدیمی مودال `YYYY-MM-DDTHH:mm:ssZ` پذیرفته می‌شوند. Z در این قرارداد، دستور تبدیل منطقهٔ زمانی نیست. شکل `.000Z` نیز پذیرفته می‌شود؛ offsetهای دیگر پذیرفته نمی‌شوند.
- اعتبار تقویمی، محدودهٔ SQL DATETIME و ترتیب شروع/پایان بررسی می‌شود؛ rollover نامعتبر مثل ۲۹ فوریهٔ سال غیرکبیسه رد می‌شود.
- دقت ثانیهٔ پیگیری قدیمی عمداً حفظ شده است؛ انتخابگرها و داده‌های قبلی به دقیقه گرد نمی‌شوند. مدت صفر مانند قرارداد فعلی مودال مجاز است؛ پایان قبل از شروع مجاز نیست.

## حفاظت گروه‌ها

- اگر هیچ‌یک از شش جدول گروه وجود نداشته باشند و دسترسی مشاهدهٔ ساختار تأیید شود، کار مستقل مجاز است؛ ساختار نیمه‌نصب‌شده یا دسترسی ناکافی، به معنی «بدون گروه» فرض نمی‌شود.
- در حضور ساختار کامل، نسخه، ایندکس‌ها و قیدهای گروه با helper موجود بررسی می‌شوند.
- تا آماده‌شدن مسیر گروه‌آگاه، نوشتن مستقل برای عضو جاری گروه رد می‌شود؛ API نمی‌تواند فقط یکی از اعضا را به‌طور پنهان تغییر دهد.
- حتی پس از خروج کار از گروه، پیگیریِ متصل به یک batch تاریخی از مسیر مستقل ویرایش/حذف نمی‌شود تا پیوند تاریخی خراب نشود.
- recipientTaskIds، groupId، expectedGroupVersion و batchId در این API مستقل پذیرفته نمی‌شوند. مسیر گروهی آینده باید شناسهٔ batch، گیرندگان صریح، نسخهٔ گروه و جلوگیری از تکرار عملیات را پیاده کند.

## اصلاح مودال

- تأیید حذف، پنجرهٔ داخلی با رنگ هشدار و نمایش کد کار/پیگیری است؛ پیام عملیات از Toast موجود استفاده می‌کند.
- clearEditor فقط وضعیت محلی را پاک می‌کند؛ هیچ درخواست نوشتنی ندارد.
- پس از حذف موفق، clearEditor فراخوانی می‌شود؛ resetEditor که قرارداد «کپی به ردیف جدید» دارد فراخوانی نمی‌شود. در نتیجه حذف، موجب POST مجدد همان متن نمی‌شود.
- دکمهٔ «ردیف جدید» همچنان با انتخاب صریح کاربر می‌تواند متن نشسته را به‌عنوان پیگیری تازه ثبت کند؛ این قابلیت حذف نشده است.
- انصراف، خطای حذف یا پاسخ ناسازگار، متن را پاک یا عملیات را موفق اعلام نمی‌کند. هنگام درخواست یا تأیید حذف، عملیات نوشتنی دیگر و انتخاب ردیف مسدودند؛ بستن والد در میانهٔ عملیات نیز متوقف می‌شود.
- Esc ابتدا تأیید حذف و سپس پنجره‌های فرزند/والد را طبق مسیر موجود می‌بندد؛ کشیدن ماوس از داخل به بیرون باعث بسته‌شدن نمی‌شود.
- پاسخ خواندن دیررس و پاسخ متعلق به کار دیگر، در فهرست جاری نمایش داده نمی‌شوند.

## حدود ایمنی

این مرحله کنترل نسخهٔ همهٔ ویرایش‌های مستقل و idempotency کامل POST را اضافه نمی‌کند. دو پنجرهٔ جدا می‌توانند متن یک پیگیری مستقل را به‌نوبت بازنویسی کنند؛ این با کنترل تعلق شناسه‌ها متفاوت است. در قطع ارتباط پس از ارسال، ممکن است سرور عملیات را انجام داده ولی پاسخ نرسیده باشد؛ پیش از تکرار ثبت، فهرست را بررسی کنید. guard رابط فقط از اجرای هم‌پوشان در همان مودال جلوگیری می‌کند.

آزمون‌های Node از دوبل SQL و fetch و VM استفاده می‌کنند؛ rollback و قفل واقعی SQL Server از آن‌ها نتیجه‌گیری نمی‌شود. آزمون تعاملی نیز با API و DatePicker شبیه‌سازی‌شده انجام می‌شود، نه با دیتابیس کاربر.

## آزمون پیشنهادی محیط واقعی

با بکاپ تازه، روی یک کار تستی مستقل که زمان ثابت و یک رویداد اتمام ثبت‌شده دارد:

1. مقدار Finish_DateTime و زمان برنامه‌ای را یادداشت کنید.
2. پیگیری تازه ایجاد و سپس ویرایش کنید. متن/زمان خود پیگیری و کپی اختیاری شرح را بررسی کنید؛ وضعیت، زمان برنامه‌ای و Finish_DateTime نباید تغییر کنند.
3. حذف را یک‌بار لغو کنید؛ ردیف و متن باید باقی بمانند.
4. همان ردیف را حذف و فهرست را دوباره بارگذاری کنید؛ نباید پیگیری جایگزین به‌طور خودکار ایجاد شود.
5. عمداً دکمهٔ «ردیف جدید» را جداگانه آزمایش کنید؛ قرارداد کپی صریح متن نشسته باید باقی باشد.

گروه یا عضو را برای آزمایش با SQL دستی ایجاد نکنید. رابط و مسیرهای نوشتنی گروهی هنوز فعال نشده‌اند.
