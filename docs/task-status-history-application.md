# تاریخچهٔ اتمام و بازگشایی کار

## پیش‌نیاز و دامنه

- ابتدا migration با شناسهٔ `20261030_001_status_history` باید در همان دیتابیس مورد استفادهٔ برنامه نصب شده باشد. این مرحله SQL جدید ندارد و دادهٔ قبلی را مهاجرت یا بازیابی نمی‌کند.
- ثبت لاگ پس از نصب این کد، در تغییر وضعیت از `/api/complete` و `PUT /api/tasks/[id]` فعال می‌شود. ایجاد اولیهٔ کار، ویرایش بدون تغییر وضعیت، تغییر مستقیم در SSMS و مسیرهای دیگر، در این مرحله رویداد وضعیت تولید نمی‌کنند. این، تاریخچهٔ عمومی همهٔ ویرایش‌ها نیست.
- API ویرایش و اتمام تا تکمیل مسیر گروهی، تغییر عضو فعال گروه را رد می‌کنند. این مرحله قابلیت گروه‌بندی را فعال نمی‌کند. نبود جدول گروه پس از بازگردانی بکاپ قدیمی، به‌تنهایی مانع کار مستقل نیست.

## حفظ زمان برنامه‌ای

- اتمام و بازگشایی به هیچ‌یک از ستون‌های زمان برنامه‌ای `DueDateTime`, `EndDateTime`, `Due_Date`, `Due_Time`, `End_Date`, `End_Time` مقدار جدید نمی‌دهند؛ هم در `Tsk_tbl` و هم در `TimeDate_tbl`.
- اتمام، `Complited=1` و `TimeDate_tbl.Finish_DateTime` را ثبت می‌کند. بازگشایی صریح، `Complited=0` و `Finish_DateTime=NULL` می‌گذارد. مقدار قبلی در تصویر قبل از عملیات باقی می‌ماند. اگر ردیف زمان وجود نداشته باشد، ردیف ساختگی ایجاد نمی‌شود؛ زمان رخداد در لاگ ثبت می‌شود.
- درخواست تکراری اتمامِ کاری که از قبل تمام شده، تاریخ اتمام را عوض نمی‌کند و لاگ تکراری نمی‌سازد.
- هشدار دربارهٔ کد قدیمی: مسیر `/api/follow` همچنان می‌تواند `Finish_DateTime` را با آخرین پایان پیگیری به‌روزرسانی کند؛ در این پچ تغییر نکرده است. بنابراین این ستون به‌تنهایی منبع انحصاریِ تاریخ واقعی اتمام نیست. زمان رخداد اتمام در `OccurredAtWall` و تصاویر رویداد ثبت می‌شود. این نویسندهٔ قدیمی ستون زمان برنامه‌ای `EndDateTime` را تغییر نمی‌دهد؛ اصلاح قرارداد آن باید همراه مرحلهٔ پیگیری گروهی بررسی شود.

## تراکنش و کنترل درخواست کهنه

- قفل زمان‌بندی، خواندن تصویر قبل، تغییر وضعیت/زمان اتمام، خواندن تصویر بعد و درج لاگ از همان اتصال و تراکنش استفاده می‌کنند. شکست درج لاگ باعث rollback تغییر وضعیت می‌شود.
- فرم فعلی، `statusIntent=preserve` را برای ذخیرهٔ بدون تغییر وضعیت می‌فرستد؛ وضعیت فعلی دیتابیس حفظ می‌شود، نه مقدار کهنهٔ فرم.
- تغییر صریح وضعیت با `statusIntent=change` و `expectedStatus` انجام می‌شود. مغایرت وضعیت فعلی با مقدار هنگام بارگذاری، خطای `STATUS_CHANGED` می‌دهد و باید فرم تازه‌سازی شود. این کنترل مقایسهٔ وضعیت است، نه نسخه‌گذاری کامل همهٔ فیلدهای فرم و نه تشخیص چرخهٔ چند تغییر متوالی که به همان وضعیت بازگشته‌اند.
- فراخوان قدیمی که بدون این قرارداد بخواهد وضعیت را عوض کند، `STATUS_INTENT_REQUIRED` می‌گیرد؛ به‌جای بازگشایی پنهانی باید فرم دوباره بارگذاری شود.
- ذخیرهٔ عادیِ کار تمام‌شده دیگر آن را موقتاً در حال انجام نمی‌کند. پس از بازگشایی صریح نیز فوراً سؤال اتمام و تنظیم زمان خودکار نمایش داده نمی‌شود.
- در جریان قدیمیِ «ذخیرهٔ فرم، سپس پاسخ به سؤال اتمام»، این دو عمل دو درخواست/تراکنش جدا هستند؛ اگر درخواست اتمام شکست بخورد، ممکن است ویرایش متن قبلاً ذخیره شده باشد. پیام خطا این تفاوت را توضیح می‌دهد.

## اطلاعات لاگ

هر رویداد شامل شناسهٔ کار، شناسهٔ عملیات، نوع `COMPLETE` یا `REOPEN`، وضعیت قبل و بعد، تصویر فیلدهای وضعیت و زمان‌بندی از هر دو جدول، زمان UTC ثبت و زمان دیواری عملیات، مسیر API و نام ورود SQL است.

- تصویرها متن شرح کار، اسامی اشخاص و مسیر ضمائم را ذخیره نمی‌کنند. با این حال فایل خروجی دادهٔ داخلی محسوب می‌شود؛ در مخزن commit نشود.
- `DatabaseLogin` نام ورود دیتابیس است، نه الزاماً هویت انسانی کاربر. تا وجود احراز هویت معتبر برنامه، `AppActor=NULL` می‌ماند.
- تاریخ‌های SQL برگشتی با برچسب UTC در تصویر، طبق قرارداد پروژه مؤلفه‌های ساعت دیواری دارند؛ برای بازنمایی/بازیابی نباید خودکار به منطقهٔ زمانی دیگری تبدیل شوند. `CreatedAtUTC` واقعاً UTC است؛ `OccurredAtWall` ساعت دیواری است.
- لاگ از طریق این API قابل ویرایش/حذف نیست و حذف کار به حذف خودکار تاریخچه منجر نمی‌شود. این ادعا به معنای مصونیت در برابر مدیر دیتابیس یا دسترسی مستقیم SQL نیست.

## خواندن و خروجی گرفتن

مسیر فقط‌خواندنی `GET /api/task-status-history` پارامترهای `taskId`، `limit` (۱ تا ۱۰۰، پیش‌فرض ۲۰) و `beforeId` را می‌پذیرد. خروجی نزولی با شناسهٔ تاریخچه است؛ شناسه‌های bigint به‌صورت رشته برمی‌گردند. صفحهٔ بعد با `nextBeforeId` خوانده می‌شود. برای دریافت لاگ نیازی به باقی‌ماندن خود کار در دیتابیس نیست.

با برنامهٔ در حال اجرا، در PowerShell ریشهٔ پروژه:

```powershell
$taskId = Read-Host "کد کار برای دریافت تاریخچه"
node scripts/export-task-status-history.mjs $taskId
if ($LASTEXITCODE -ne 0) { throw "دریافت تاریخچه ناموفق بود." }
```

اسکریپت پیش‌فرض از سرور محلی پورت ۳۰۰۰ می‌خواند، همهٔ صفحات را جمع می‌کند و فایل JSON با نام `task-status-history-...json` در پوشهٔ جاری می‌سازد. آدرس سرور HTTP(S) دیگر را می‌توان به‌عنوان آرگومان سوم ارائه کرد؛ نام کاربری/رمز در URL پذیرفته نمی‌شود. هیچ کوئری تغییردهنده یا بازگردانی اجرا نمی‌کند. اگر برنامه در شبکه منتشر است، دسترسی به این API مانند دیگر APIهای داخلی باید در لایهٔ استقرار محدود باشد؛ این مرحله سامانهٔ احراز هویت جدید اضافه نمی‌کند.

## بازگردانی کنترل‌شده

بازگردانی خودکار در این مرحله فعال نیست. فایل خروجی فقط مدرک بررسی و تهیهٔ عملیات بازیابیِ موردی است، نه دستور اجرای SQL.

اگر بعداً نیاز به بازگردانی رخ داد:

1. بکاپ تازه و خروجی تاریخچهٔ همان کار تهیه شود.
2. `HistoryID` و تصویر قبل/بعدِ مدنظر انتخاب و با وضعیت فعلی و ردیف‌های واقعی زمان تطبیق داده شود؛ تغییرات جدیدتر نباید ناخواسته بازنویسی شوند.
3. اختلاف فیلدها و اثر احتمالی بر گروه و تداخل زمانی پیش‌نمایش و تأیید شود.
4. بازیابی موردی با قفل، کنترل هم‌زمانی و تراکنش واحد اجرا شود و لاگ تازهٔ `RESTORE` با `RestoresHistoryID` همان کار ثبت شود؛ تاریخچهٔ قبلی تغییر نکند.

این مسیر بازیابی اجرایی هنوز پیاده‌سازی نشده است. برای کار قبلی که با بکاپ اصلاح شده، هیچ بازگردانی تازه‌ای لازم یا اجرا نشده است.

## آزمون روی محیط واقعی

آزمون‌های Node شامل دوبل SQL، VM و fetch هستند؛ رفتار واقعی درایور SQL Server، قفل‌ها و rollback آن را اثبات نمی‌کنند. بررسی تعاملی فرم نیز با API و فرزندان شبیه‌سازی‌شده انجام شده است، نه اتصال به دیتابیس کاربر.

پس از نصب، فقط روی یک کار تستی مستقل با زمان ثابت مشخص: زمان‌های شروع/پایان را یادداشت کنید؛ یک‌بار اتمام و یک‌بار بازگشایی صریح انجام دهید؛ ثابت‌ماندن زمان برنامه‌ای را بررسی و خروجی تاریخچه را دریافت کنید. انتظار دو رویداد `COMPLETE` و `REOPEN` است. پیش از تأیید این آزمون، موفقیت روی محیط واقعی فرض نشود.
