# تاریخچهٔ وضعیت کار — مرحلهٔ اول

## وضعیت فعلی

این مرحله فقط جدول مستقل `dbo.TaskStatusHistory` را آماده می‌کند. **هنوز هیچ لاگ خودکاری ثبت نمی‌شود و اشکال تغییر زمان پایان یا بازگشایی فرم اصلاح نشده است.** تغییرات برنامه در مرحلهٔ بعد، پس از تأیید نصب جدول، ارائه می‌شوند. جدول‌های گروه‌بندی پیش‌نیاز نیستند.

اسکریپت migration کار، زمان‌بندی یا پیگیری موجود را تغییر نمی‌دهد و دادهٔ تاریخی ساختگی ایجاد نمی‌کند. بازگردانی دیتابیس قدیمی ممکن است این جدول را نیز حذف کند؛ پس آمادگی آن باید در سرویس آینده بررسی شود. پیش از نصب، از دیتابیس فعلی پشتیبان تازه تهیه شود.

## نصب

`database/migrations/20261030_001_task_status_history.sql` را در SSMS، در پنجرهٔ جدید بدون تراکنش باز اجرا کنید. مقصد اسکریپت `WorkDB` است. اگر نام دیتابیس برنامه متفاوت است، این نسخه اجرا نشود. اسکریپت از تراکنش صریح، XACT_ABORT، قفل نصب و تأیید ساختار استفاده می‌کند. اجرای مجدد، جدول و ردیف‌های تاریخچه را پاک نمی‌کند؛ ساختار ناشناخته یا ناقص را خودکار تغییر نمی‌دهد.

## محتوای تاریخچه و قرارداد مرحلهٔ بعد

- OperationID یکتا برای شناسایی عملیات و جلوگیری از ثبت تکراری.
- TaskID و وضعیت قبل/بعد با عملیات COMPLETE، REOPEN یا RESTORE.
- BeforeState و AfterState به‌شکل JSON معتبر؛ سرویس باید نسخهٔ ساختار JSON، اطلاعات وضعیت و تصویر زمان‌های هر دو جدول را ثبت کند.
- تصویر زمان‌بندی شامل TaskID، شناسه‌های TimeDate، اولویت، حالت زمان ثابت، مدت، DueDateTime، EndDateTime، تاریخ/ساعت‌های جداگانه و Finish_DateTime است. متن شرح کار، رمزها، مسیر پوشه و اطلاعات اشخاص در این تصویر لازم نیست و نباید بی‌دلیل کپی شود.
- CreatedAtUTC ساعت رویداد دیتابیس با مبنای UTC؛ OccurredAtWall ساعت دیواری برنامه است و باید سرویس آن را صریحاً ارسال کند. این دو مبنا با یکدیگر اشتباه نشوند.
- DatabaseLogin نام اتصال SQL است، نه ادعای شناسایی کاربر انسانی. AppActor فقط در صورت وجود احراز هویت معتبر در خود نرم‌افزار پر شود؛ در غیر این صورت NULL بماند.
- Source مسیر معتبر سمت سرور است، نه رشتهٔ قابل اعتمادِ ارسالی از مرورگر.
- RestoresHistoryID برای اتصال بازیابی به تاریخچهٔ همان کار؛ قید مرکب اجازهٔ ارجاع به سابقهٔ کار دیگری نمی‌دهد.
- جدول عمداً به Tsk_tbl کلید خارجی ندارد؛ حذف کار نباید تاریخچه را حذف یا عملیات حذف فعلی را به‌دلیل این جدول مسدود کند. هیچ ON DELETE CASCADE وجود ندارد.
- قرارداد سرویس آینده append-only است: ثبت رکورد جدید، نه UPDATE یا DELETE رکورد قدیمی. این migration به‌تنهایی مانع تغییر دستی توسط مدیر دیتابیس نمی‌شود.
- ثبت تاریخچه و تغییر وضعیت باید روی همان اتصال و در همان تراکنش باشند. نبود جدول یا شکست درج لاگ باید مانع تغییر وضعیت شود، نه اینکه خطا نادیده گرفته شود.
- COMPLETE فقط پایان واقعی را ثبت کند؛ زمان برنامه‌ریزی‌شده حفظ شود. REOPEN صریح باشد و پایان واقعی قبلی در تاریخچه بماند. ذخیرهٔ معمول فرم نباید ابتدا وضعیت را اجباری صفر کند.
- بازیابی آینده نیازمند بررسی اختلاف و تأیید صریح، کنترل تغییرات همزمان، حفظ زمان‌های جدیدتر و ثبت رویداد RESTORE است. هیچ endpoint بازیابی در این مرحله ایجاد نشده است.

## دسترسی خواندنی به تاریخچه

پس از اتصال کد برنامه و ایجاد رویدادها، می‌توان از پرس‌وجوی زیر استفاده کرد. نتیجهٔ خالی بلافاصله پس از نصب طبیعی است. مقدار نمونهٔ TaskID باید با کد کار موردنظر جایگزین شود.

```sql
DECLARE @TaskID int = 202;
SELECT TOP (100)
    HistoryID, OperationID, TaskID, Action, BeforeStatus, AfterStatus,
    CreatedAtUTC, OccurredAtWall, Source, DatabaseLogin, AppActor,
    RestoresHistoryID, BeforeState, AfterState
FROM dbo.TaskStatusHistory
WHERE TaskID = @TaskID
ORDER BY HistoryID DESC;
```

تاریخچه، snapshot پیش از نصب یا تغییرات خارج از برنامه را از گذشته بازسازی نمی‌کند. بازیابی دادهٔ قدیمی این کار توسط کاربر انجام شده و در برنامهٔ فعلی نیست.

## آزمون و محدودیت

آزمون `tests/task-status-history-schema.test.mjs` فقط ساختار متن SQL و نبود دستورات تغییر داده‌های فعلی را کنترل می‌کند؛ SQL Server، parse واقعی T-SQL، قفل، ایجاد جدول و rollback را اجرا نمی‌کند. موفقیت این آزمون معادل نصب موفق نیست. اجرای migration و نتیجهٔ نهایی آن روی SQL Server کاربر باید جداگانه تأیید شود.
